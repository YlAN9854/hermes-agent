## 使用情境(谁、何时、为什么)

**用户**:在 dashboard 里用 Hermes agent 干活的人(写代码 / 调研 / 多步任务)。

**关键定位(与用户反复敲定)**:平时用户**只管对话、不必关心 context**。
ContextVis **不是常驻仪表盘**,而是**当 agent 开始出错、或窗口将满、或系统要动手压缩时**
才介入的「上下文治理台」。所以一切需求都围绕**异常时刻的可读、可追溯、可治理**,
而非日常装饰。

**中心真相(CLAUDE.md 第 1 条)**:上下文 = 在固定容量里不断填充。任何需求最终都要
回答四问之一——**装了多少 / 由什么构成 / 怎么涨上来 / 该拿它怎么办**。下面按这四问 +
一个工作流层需求组织。

## C. 可治理 · 用户主动 —— 命运编辑(白盒的第三层)

> 视图从"观察"升级到"治理":agent 出错 / 窗口将满时,用户**手动控制**上下文。
> 不另造引擎,而是**可视化并接管 Hermes 既有压缩**(基线见 [compression-baseline.md](compression-baseline.md))。

| # | 用户需求 | 解决方案 | 状态 |
|---|---|---|---|
| R6 | **标记每块的命运**(保留/折叠/丢弃) | 检视器命运按钮 + treemap 叠加渲染(drop 红斜划 / fold 虚线边 / keep 实线边);命运存前端 `fateMap`,不污染后端真值 | ✅ 方向 A 阶段 1 |
| R7 | **下手前预见影响**(会释放多少、占用降到哪) | `projectFates` 纯函数投影(drop 释放 100% / fold 80% / keep 0,对齐 `summary_target_ratio`)+ 占用条幽灵刻度 + 预览行 `78%→52%` | ✅ 方向 A 阶段 2 |
| R8 | **真的把噪音删掉**(动真实上下文) | `context.apply` RPC:按 `sourceRefs.messageIndex` 删消息 → 复用 `_sanitize_tool_pairs` 缝合 → 写回 history、占用即时回落 | ✅ 方向 A 阶段 3 v1(drop) |
| R9 | **误操作可回退** | 一步内存撤销 `_contextvis_undo`(apply 前快照),`history_version` 陈旧校验防过时视图误删 | ✅ |
| R10 | **把一段折成摘要、而非整条删掉**(保留要点、丢掉冗长) | A-v2 fold:复用 `_generate_summary(turns, focus_topic)` 把 fold 块摘要化,`context.fold` 落地 | ✅ A-v2 fold |
| R11 | **把跨类型、同语义的几块一起合并压缩**(见下 §E 工作流) | A-v2 fold 的**单隐式组**:多选 chunk(可跨 user/tool_call/tool_result、可非连续)+ 可选重心 prompt → 一条摘要 | ✅ A-v2 fold |

> R10/R11 是同一引擎(fold)的两种用法:R10 是组大小=1,R11 是组大小>1 跨类型。
> v1 范围已与用户敲定:**仅非对话态 treemap 交互**(避开 running 闸冲突 + messages↔history
> 对账两暗礁)、**单隐式组**(多次操作即等价多组)、**action 原子化**(一次只 fold 或只 drop)、
> **支持非连续**(靠自动补全工具对 + `_sanitize_tool_pairs` + 透明预览兜住)。

> 这是用户主动治理(§C)的**对偶**。

| # | 用户需求 | 解决方案 | 状态 |
|---|---|---|---|
| R12 | **系统别静默压缩我的上下文**——到阈值要压时先让我看、让我定 | 压缩闸门第一阶段:拦 [conversation_loop.py:3812](../agent/conversation_loop.py#L3812) → treemap 画系统计划 + 占用投影 → 继续/推迟(300s 超时自动继续,无人值守天然安全)。复用审批基建 | ✅ 压缩闸门一阶段 |
| R13 | **在系统压缩前直接改它的方案**(接受 / 编辑后继续 / 编辑后让系统补压) | 压缩闸门第二阶段:闸门内开放 §C 的 drop/fold 编辑。**先解两暗礁**:running 闸冲突、messages↔history 对账 | ⬜ |
| R14 | **系统帮我识别该删什么**(我不想从零逐块判断) | 建议策略注册表:系统预 mark 一份建议 fate(失败工具结果 / 重复读同一文件 / 久未触及支线)→ 用户增删确认。喂给同一个 fold/drop 操作,UI 不变 | ⬜ |

## E. ★ 工作流需求 —— 主线/支线在同一 session 下并行

> **本文新立的顶层需求**,统摄 §C 多条子方案。这条最贴 ContextVis「治理」的真实用例。

### 痛点

和 AI agent 协作时,任务天然分**主线**(当前要交付的事,如写一个功能)与**支线**
(中途冒出的、与主线无关的岔路,如"顺便解释下这个系统函数的特性")。支线一旦进了上下文,
就**永久稀释**主线的工作记忆,还在窗口里占地、推高压缩频率。

**今天用户只能靠 fork session / 主动切 session 来隔离支线**——这是沉重的负担:要预判
哪段是支线、手动开分身、来回切、事后还难合并。**多数用户不会这么做,于是支线噪音累积,
主线越聊越糊。**

### 目标

让用户**在同一 session 下持续工作**:主线靠 context 治理**持续推进**,支线**完成后即收纳
**(折成一句摘要)或**即删除**——不必 fork、不必切 session。把"开分身"这种**会话级**的
笨重操作,降维成"在 treemap 里框几块、点折叠"的**上下文级**轻操作。

### 解决方案(分解到子需求)

| 子需求 | 解决方案 | 状态 |
|---|---|---|
| E1 **收纳支线**:把一个支线涉及的跨类型块(用户提问 + 相关工具调用 + 结果)一起折成摘要 | = R11(A-v2 fold 单隐式组,跨类型 + 非连续 + 重心 prompt) | ✅ A-v2 fold |
| E2 **保主线不被稀释**:选择性保留主线、收纳/删除支线 | = R6+R8+R10(命运编辑:keep 主线、fold/drop 支线) | ✅/⬜ |
| E3 **识别哪些块属于哪条支线**:用户不必逐块辨认 | **被 [turn-band.md](turn-band.md) 吸收**:不再造"主题聚类 ChunkStrategy",改由 regime 检测器产**逐轮 topic**,在 turn 粒度上识别主线/支线 | ◑ 重定向至 turn 带 |
| E4 **便于框选同一支线的块**:同语义的块在视图上聚拢、好框选 | **被 [turn-band.md](turn-band.md) 取代**:主轴从"类型"翻成"turn"(纵向时间序 + 逐轮主题着色),同 topic 的轮天然聚拢;旧类型带留作 toggle。E4 的"语义重排"搁置 | ◇ 设计定稿(turn 带) |

> **架构关键(让 E 系列省力的根)**:**「选什么」与「fold 操作」彻底解耦**。fold 引擎只吃
> 「一组 message + 可选 prompt → 一条摘要」,**完全不关心这组怎么选出来**。于是 E3/E4
> (语义分块、语义排列、智能建议)全是**选择层的增量**,不触碰 fold 落地路。手动多选(R11)
> 先跑通,语义/智能选择后叠加,输出格式一致。

> **E3/E4 的归宿(本次讨论定型)**:见 [turn-band.md](turn-band.md)。主轴从"类型优先"翻成
> **"turn 优先"**——纵向时间序、与 TUI 同向、逐轮主题着色。这恰好踩在 E4 红线的安全侧
> (**时间序保底**,语义聚类不取代时间轴),且把"语义化 chunk"的正式表达定为"**逐轮主题**"
> (复用 regime 检测器,不造新分块器)。turn 带在大窗口下还是 ContextVis 的**主操作台**。

### E0 ★ 自适应启动:别在森林里打扰,有主线时才介入(本文后补,统摄 E3)

> 多轮讨论后的**上位结论**:E3 的落点从"独立语义视图(E4)"挪到"**给压缩装一个任务态
> 总开关**"。设计与论证见 [regime.md](regime.md)。

session 有两态:**① 森林**(turns 独立,Hermes 自带压缩 + 记忆已够,ContextVis 应**休眠**)、
**② 主线**(长期目标,ContextVis 主战场)。原理:**森林里位置式压缩本就语义正确(留近=相关),
主线里位置偏离语义**——ContextVis 是"**位置式压缩将要背叛你的任务时才启动的纠偏器**"。

| 子需求 | 解决方案 | 状态 |
|---|---|---|
| E0a **森林里别烦我** | 检测器判 ①/②(启发式 + **LLM 语义**);① 态闸门闭嘴、静默自动压(像普通 Hermes) | ✅ regime 已建成 |
| E0b **有主线时,压缩前让我把关** | **两级闸门**(regime ∧ collision):有主线 **且** 这次压缩会伤到它,才打断 | ✅ regime 已建成 |
| E0c **压在对的焦点上** | 检测出的 `focus` 喂 `_generate_summary` 的 `focus_topic`,保相关压无关(检测已产 focus,接线待做) | ◑ focus 已检出 |
| E0d **扫出已有 context 里的死重支线** | 按需**深析**产出死重清单(收益排序)→ 喂闸门 + 方向 A 主动清理 | ⬜ 后续 |

> E0a/E0b **已建成实测**:检测器(启发式第一刀 + LLM 语义第二刀)+ 两级门控,森林静默、任务才弹,
> 见 [regime.md](regime.md)。E3「识别支线」由此**被 E0 吸收并重定向**:不再追求全局语义聚类/独立 treemap,而是
> **检测器在压缩时刻产出"护住的焦点 + 死重清单",预填 fateMap、复用已建成的 fold/drop/闸门**。
> 边界:**记忆(MEMORY.md)管跨 session 稳定事实;ContextVis 管 session 内在飞工作态**,互补不重叠。

## 贯穿性设计约束(约束所有解决方案,来自 CLAUDE.md 不变量)

这些不是"需求",是**所有方案都不可破的底线**:

- **token 真实计数**:比例与总量必须真(可信度地基);逐块绝对值可为缩放重建,但**不冒充精确**。
- **类型恒定可辨**:5 类型在所有形态以恒定方式区分(web 用色)。
- **量级编码 token**:面积 ∝ token,比例关系神圣。
- **时间是一条轴**:逐轮累积可回放(R5);任何"语义/聚类"视图(E4)只能并存、不能取代时间序。
- **干预透明**:每次删/折/保留都让用户看到"改了什么 + 系统如何缝合衔接"(R7 预览 + §D 闸门)。
- **三层隔离 + 渲染可插拔**:渲染层永不直接依赖宿主结构;换分块策略(E3)/换皮肤只动适配器与策略注册表,契约不变。
- **白盒优先于美观**:克制、高密度、忠于数据。
